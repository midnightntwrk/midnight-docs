# Managing Private State with Witnesses

In the Midnight Network, ensuring data privacy while maintaining verifiable state is achieved through **Zero-Knowledge (ZK) proofs**. A core concept in building Midnight dApps is the **witness**—data that is known to the user (the prover) but kept hidden from the network (the verifiers).

This guide covers how to define and use witnesses in the **Compact DSL**, integrate them using the **Compact JavaScript implementation**, and troubleshoot common issues.

---

## Core Concepts

Before diving into code, it's important to understand the role of a witness in a Midnight dApp:
1. **Public State (Ledger)**: Data stored on the Midnight blockchain that anyone can read.
2. **Private State**: Data kept locally by the user.
3. **Witness**: A function or variable that supplies private data to a smart contract circuit during local execution. The circuit uses this data to generate a ZK proof, which is then submitted to the network. The network verifies the proof without ever seeing the witness data.

## Step-by-Step Walkthrough: A Private Access Code

Let's build a simple circuit where a user must provide a secret access code to update a public counter. The network will know the counter increased, but will never know the access code used.

### 1. Defining the Circuit in Compact

In your Compact contract, you define a `witness` block. This tells the compiler that the circuit expects external, private input during execution.

```compact
// access_control.compact
pragma language_version >= 0.14.0;

export ledger counter: Uint<32>;

// The network knows the hash of the secret code, but not the code itself.
export const SECRET_HASH: Bytes<32> = 
  0x1234567890abcdef1234567890abcdef1234567890abcdef1234567890abcdef; // Example hash

// Define the witness structure
witness access_witness(): Bytes<32>;

export circuit increment_counter(): [] {
    // 1. Fetch the private data via the witness
    const secret_code = access_witness();

    // 2. Verify the secret code matches the expected hash
    // The hash function is evaluated locally, and a proof of correct execution is generated.
    const computed_hash = persistentHash<Bytes<32>>(secret_code);
    assert(computed_hash == SECRET_HASH, "Invalid access code");

    // 3. Update the public ledger
    counter = counter + 1;
}
```

### 2. Providing the Witness in TypeScript

When the Compact compiler processes your contract, it generates a JavaScript implementation in the `managed/` directory. The generated `Contract` class requires a **witnesses object** whose keys match the witness names declared in your `.compact` file.

Each witness function receives a `WitnessContext` carrying the current ledger view, private state, and contract address, and returns a tuple of the updated private state and the witness value.

```typescript
import { Contract, Ledger } from './managed/access_control/contract/index.js';
import { WitnessContext } from '@midnight-ntwrk/compact-runtime';

// Define the shape of your private state
type AccessControlPrivateState = {
  readonly secretCode: Uint8Array;
};

// Create a factory for initial private state
const createPrivateState = (secretCode: Uint8Array): AccessControlPrivateState => ({
  secretCode,
});

// Implement witnesses — keys must match Compact witness names exactly
const witnesses = {
  access_witness: ({
    privateState,
  }: WitnessContext<Ledger, AccessControlPrivateState>): [
    AccessControlPrivateState,
    Uint8Array,
  ] => [privateState, privateState.secretCode],
};

// Instantiate the contract with the witnesses object
const contract = new Contract(witnesses);
```

Once instantiated, you can call the circuit through `contract.impureCircuits`:

```typescript
// Build a circuit context with ledger state and private state
const context = {
  originalState: {
    counter: 0n,
  },
  privateState: createPrivateState(
    new Uint8Array([/* ... 32 bytes of secret data ... */])
  ),
  contractAddress: '0x...',
  transactionContext: {},
};

// Execute the circuit locally — this invokes access_witness() automatically
const { result, context: updatedContext } =
  contract.impureCircuits.increment_counter(context);

console.log('New counter value:', updatedContext.originalState.counter);
```

For a complete walkthrough of importing the generated module, writing witnesses, calling circuits, and running tests, see [Using Compact contracts from JavaScript](./compact-javascript-runtime).

## Troubleshooting & Best Practices

When working with witnesses, you might encounter a few common pitfalls. 

### 1. "Witness not provided" or "Missing witness" Error
**Cause**: The `Contract` constructor validates that every witness declared in Compact has a matching key in the witnesses object. If any key is missing, the constructor throws.
**Solution**: Ensure every key in your witnesses object *exactly* matches the name of the witness defined in your `.compact` file.

### 2. Non-Deterministic Witnesses
**Cause**: If your witness function returns different values if called multiple times during the same execution context, proof generation will fail. The prover evaluates the circuit multiple times to generate constraints.
**Solution**: Ensure your witness functions are **pure** and **deterministic**. If you need to generate a random value, generate it *once* before calling the contract method, store it in a variable, and have the witness function return that variable.

```typescript
// BAD: Generates a new random value every time it's called
const witnesses = {
  get_random_nonce: ({ privateState }: WitnessContext<Ledger, MyPrivateState>) =>
    [privateState, crypto.getRandomValues(new Uint8Array(32))],
};

// GOOD: Value is fixed for the duration of the execution
const fixedNonce = crypto.getRandomValues(new Uint8Array(32));
const witnesses = {
  get_random_nonce: ({ privateState }: WitnessContext<Ledger, MyPrivateState>) =>
    [privateState, fixedNonce],
};
```

### 3. State Commitment Mismatches
**Cause**: You updated public state in the ledger based on private state, but the private state was invalid according to the circuit's `assert` statements.
**Solution**: Always validate inputs on the client side before invoking the contract to save time. Proof generation is computationally expensive, so failing early in the UI is better than failing during proof generation.
